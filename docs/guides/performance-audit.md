# 성능 전수조사 (버퍼·멈춤·느린 곳)

## 개요

사용자 흐름마다 화면이 멈추거나(긴 작업), 늦게 반응하거나(입력에서 페인트까지), 엔진에 같은 일을 여러 번 시키거나(호출 수·크기),
쉴 때도 일하거나(유휴 폴링), 오래 쓰면 메모리가 느는지(소크)를 웹(Chromium)과 데스크톱(Electron)에서 쟀다. 재생 자체(모니터 재생
루프, 소리 재생, 엔진 미리 읽기)는 다른 작업(feat/playback)이 맡아 여기서는 재기만 하고 고치지 않았다.

결론: 작은 편집본(클립 수십 개)은 이미 빠르다(클릭에서 페인트까지 20~30ms, 긴 작업 없음, 유휴 CPU 0.13%). 느려지는 곳은 클립이
많을 때(200개)의 줌과 실행 취소 연타, 그리고 스티커 탭을 처음 열 때였다. 셋 다 화면 쪽에서 고쳤고(아래 2절), 남은 큰 비용은
엔진의 `sequence.inspect` 크기(200 클립 429KB)와 재생 쪽이다(3절).

환경: WSL2 16코어, 다른 워크트리가 Rust 를 빌드하는 중(부하 평균 10~15)이라 수십 ms 차이는 흔들린다. 전후 비교는 같은 스크립트를
번갈아 돌렸고(데스크톱은 main 의 빌드와 이 브랜치의 빌드를 두 번씩), 숫자는 범위로 적는다.

```bash
npm run build -w apps/web && node scripts/perf-survey.mjs --json web-1440.json
node scripts/perf-survey.mjs --width 390 --port 4334 --json web-390.json
npm run build -w apps/desktop && xvfb-run -a node scripts/perf-survey-desktop.cjs              # 이 트리
xvfb-run -a node scripts/perf-survey-desktop.cjs /path/to/other/checkout/apps/desktop        # 비교 대상
```

## 3. 엔진·재생 쪽 제안 (이 작업에서 고치지 않음)

- **R1 `sequence.inspect` 를 가볍게**: 클립마다 고유 효과 파라미터를 다 싣지 말고 화면이 쓰는 것(위치·길이·이름·링크·효과 id 목록·키프레임
  수)만 기본으로, 파라미터는 `{params: true}` 또는 클립 하나를 읽는 커맨드로. 200 클립 429KB·napi 11.8ms 에서 크기 1/5 이하가 목표. 편집마다
  2번 읽으므로 데스크톱 왕복 33~46ms 가 절반 이하로. 다음 단계는 revision 사이 바뀐 클립만 주는 증분 읽기.
- **R2 `drainEvents` 에 플레이헤드 변화**: 지금은 폴링마다 `playhead()` 를 따로 부른다(유휴 10초에 41번). 엔진이 `playheadChanged {tick}`
  이벤트를 내면 화면은 `playhead()` 를 뺄 수 있다(유휴 메시지 절반).
- **R3 데스크톱 프레임 전달**: 2MB 프레임을 엔진 프로세스에서 렌더러로 복사한다(왕복 29ms 중 약 15ms). 렌더러가 표시 크기만큼만 요청하고
  있는지(scale 0.5 고정이 아닌지) 먼저 보고, 다음은 공유 메모리(Electron 의 SharedArrayBuffer 는 프로세스를 넘지 못하므로 엔진을 렌더러
  쪽 Worker 로 옮기거나, 메인 프로세스 경유 없이 utility process 와 렌더러 사이 포트를 유지한 채 YUV 4:2:0(1/2.7 크기)로 보내기).
- **R4 모니터와 타임라인이 같은 시퀀스 읽기를 나누기**: `monitor/controller.ts` 의 readSequence 가 타임라인 store 가 읽은 결과(같은 revision)를
  쓰면 편집마다 `sequence.inspect` 가 2번에서 1번이 된다. 재생 작업(feat/playback)과 겹치는 파일이라 넘긴다.
